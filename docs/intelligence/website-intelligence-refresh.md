# Website intelligence refresh

## Slice 6D.2B durable refresh, Product Channel, and Calendar

Website refresh scheduling is profile-scoped and supports `MANUAL`, `DAILY`, `WEEKLY`, and `MONTHLY` policies with an IANA timezone and one bounded next occurrence. Due materialization is owner-scoped, row-locked, unique by profile and scheduled timestamp, and emits `website.refresh.materialized`; replay returns the existing job. Execution records `QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`, or `SKIPPED`, reuses the refresh idempotency key, and never retries a completed job. Disabled sources and `BLOCKED`/`REVIEW_REQUIRED` classifications fail closed; the global intelligence emergency stop and disabled switch also skip work safely.

The durable refresh ledger is `intelligence_website_refresh_jobs`; source profiles retain next/last refresh timestamps, timezone, policy version, target type, and failure code. The shared publishing worker claims refresh jobs with PostgreSQL leases, claim counts, and stale-lease recovery; it never dispatches connector mutations. Recovery exposes a catalog for the twelve classified failure codes and idempotent owner-scoped actions. Calendar exposes one server-derived due event per scheduled profile for all supported target types, while Product Channel remains read-only and server-derived. Operations/System Doctor expose refresh backlog, worker/scheduler registration, integrity counters, next due, last success, and recovery registration without secrets or raw content. Catch-up remains bounded to one next occurrence per materialization pass.
