## Reviewed defects / gaps

- **QA-P3-FIN-001** (CONFIRMED, P1): The January cost 200.01 is still used after a February UNKNOWN revision of the same key. The February summary reports contribution -103.04 and no missing inputs. _cost_evidence_rows filters UNKNOWN rows before choosing the latest version, resurrecting the superseded known row. Impact: A seller can receive a qualified profit/loss estimate based on acquisition evidence they explicitly marked unknown. Proposed correction: Select the latest applicable cost revision first, then preserve UNKNOWN as a blocker; retain valid historical as-of behavior and cost lineage. Implement only with separate remediation authorization.
- **QA-P3-IDEM-001** (CONFIRMED, P1): After recording delta 1, reusing the same key with delta 99 returns HTTP 200 and the original balance. Duplicate lookup checks only item/key, not movement identity. No extra stock was added; the defect is silent acceptance of conflicting intent. Impact: A seller or retrying client can believe a requested correction succeeded although a different earlier movement was returned. Proposed correction: Define canonical semantic replay identity and reject changed movement payloads while retaining identical retry and concurrency safety.
- **QA-P3-IDEM-002** (CONFIRMED, P1): Replaying the recorded sale with amount 999999 returns HTTP 201/idempotent true and the old event. Both preflight and uniqueness-recovery paths return the existing event without checking amount/type/reference identity. Existing data is not overwritten. Impact: Conflicting sale or refund evidence can be silently discarded while a client sees a success response, obscuring reconciliation errors. Proposed correction: Compare normalized authoritative event identity in both replay paths and return a conflict for changed evidence, without weakening identical-delivery deduplication.
- **QA-P3-IDEM-003** (CONFIRMED, P2): A resolve request using the acknowledge key returns HTTP 200, the old transition ID and ACKNOWLEDGED state. _transition looks up owner/key but does not compare signal, target state or note. Impact: The displayed/requested HUMAN intent and audit transition may disagree, making operational review unreliable. Proposed correction: Validate semantic transition scope and target under the canonical owner/key lock; preserve identical concurrent replays.
- **QA-P3-SIGNAL-001** (CONFIRMED, P1): After the same item is replenished from 0 to 20 and rescanned, its signal remains ACKNOWLEDGED/critical with evidence available 0, source version v1 and confidence 0.90. The scan upserts current matches but does not invalidate no-longer-matching signals. Impact: A seller may waste time or make unnecessary replenishment decisions from a high-confidence obsolete recommendation. No automatic procurement was executed. Proposed correction: Reconcile emitted fingerprints against current source state, retaining history while transitioning obsolete claims to a truthful noncurrent state. Do not auto-approve any business action.
- **QA-P3-SOURCE-001** (CONFIRMED, P1): The Flipkart summary contains only fake orders, canonical_order_fallback true and event_count 0, but synthetic_provider false. The flag inspects FinancialEvent source_type only and ignores fake order totals/provenance. The UI uses this flag to choose Synthetic fixture versus Canonical evidence. Impact: A rehearsal can be presented as non-synthetic financial evidence, undermining trust in seller readiness and forecasts. Proposed correction: Propagate synthetic/trust provenance through every contributing canonical source, never promote missing source classification to real/verified evidence.
- **QA-P3-UX-001** (CONFIRMED, P2): After resolving a card, choosing Resolved shows no card although the detail API reports RESOLVED and history. The select updates ngModel only; load() requests include_resolved only when called later, so the current dataset excludes resolved rows. Reproduced on desktop/mobile. Impact: Sellers cannot reliably find completed work through the offered status filter and may think their review history was lost. Proposed correction: Trigger an authoritative reload on the status change and keep loading/error/context feedback; do not remove the filter or relax the browser assertion.
- **QA-P3-GAP-001** (CONFIRMED, P2): The supported authority overwrites one calculation row per scope/version. A later refund keeps the ID but changes metrics; the list is current projections, not immutable versions. Lineage lists event IDs but not the cost evidence used. This is a missing workflow, not a broken existing immutable-history contract. The final test validates the actual mutable contract. Impact: A seller cannot reconstruct the exact earlier profitability calculation from this projection alone, even though source events remain persisted. Proposed correction: Define whether retained calculation versions are required; reuse canonical snapshot/audit patterns and include applicable cost/source identities. Do not relabel current projections as immutable history.
- **QA-P3-GAP-002** (CONFIRMED, P2): The request-action authority returns approval_required and says the recommendation is recorded, but it adds no durable approval/action record. There is no approve/reject/failed-execution/retry lifecycle in this authority. The default-deny external boundary is working and was not bypassed. Impact: A first-time seller may mistake a requested or acknowledged signal for a saved authorization or completed action. Proposed correction: Clarify messaging and route only supported actions to their existing canonical HUMAN authorities; do not add a duplicate approval system or expose remote execution in QA.
- **QA-P3-GAP-003** (CONFIRMED, P2): The workspace tells the seller to create a product stock record, but exposes filters, adjustments, ledger and mapping only for existing items. Its canonical creation API exists; this suite seeds it through that API. Product master inventory fields are a separate model and are not a demonstrated replacement for this missing handoff. Impact: API fixtures can exercise populated inventory, but a first-time seller can still encounter a UI onboarding dead end. Proposed correction: Plan an explicit canonical creation/handoff using the existing API, with opening balance provenance and HUMAN review. Do not duplicate stock ledgers.
- **QA-P3-A11Y-REVIEW-001** (SUSPECTED, P2): All 107 original repeated-state target occurrences were examined after real scrolling using axe. 101 passed and six caption occurrences remain incomplete; no contrast violation was confirmed. A separate financial-loss screen also retains four incomplete mobile nodes. These are manual-review tasks, not confirmed WCAG failures and not resolved findings. Impact: Automated testing cannot yet establish readability of every mobile caption/obscured table element; first-time seller comprehension and assistive-technology behavior still need review. Proposed correction: Manually review clipped captions and table reading/keyboard behavior, then authorize a focused responsive/accessibility correction if needed. Retain full-document axe checks and do not suppress incomplete results.
